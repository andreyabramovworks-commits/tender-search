# Tender Search

Ежедневный сбор кандидатов из обычного поиска TenderLand в Google Таблицу. Python 3.12, PostgreSQL 17, SQLAlchemy, Alembic, Docker Compose. Нейросети и AI-функции TenderLand не вызываются.

Скрипт ищет три направления по исходным ключевикам: сцены, физическая защита от БПЛА и строительные леса. Ключевики находятся в `config/queries.json`; сочетания с `++` передаются в родном синтаксисе TenderLand. Pro и Standard используют общий механизм веб-поиска, но проверяются и выполняются оба режима. По умолчанию проверяются названия. Дополнительный поиск по документации включается через `SEARCH_SCOPES=title,documents`; причины включения всегда сохраняют режим, область и точный запрос.

При замере 5 ноября 2026 года `металл++конструк` дал 92 текущие закупки по названию и 11 362 по документации; `сцен` — 100 и 4 670. Поэтому для первой рабочей версии документация выключена: исходные широкие слова дают слишком большую и шумную выборку. Все ключевики используются без удаления. Для расширения поиска следует уточнить словарь и затем явно включить документацию.

## Поведение

- Каждый ежедневный запуск полностью сверяет **текущие закупки** по фильтру актуальности TenderLand в доступном шестилетнем интервале. Это сознательно дороже инкрементального поиска только за вчера: поздно добавленная старая закупка тоже может попасть в подборку. Это не обещание охвата закрытых или отсутствующих у TenderLand источников.
- Из основной карточки собираются номер, название, заказчик, ИНН, цена, место исполнения, даты, статус и первоисточник. Дополнительная карточка даёт ID и названия лотов, валюту и сроки исполнения, если источник заполнил их. Неизвестные значения остаются пустыми. Даты источника сохраняют его часовой пояс; время работы скрипта показывается по Москве.
- Одна строка на стабильный ID TenderLand. Несколько запросов/категорий объединяются. Изменения обновляют ту же строку и сохраняются в истории PostgreSQL. Разные ID с одинаковыми названиями автоматически не объединяются.
- В Google Sheets используются адресные записи в фиксированные строки с проверкой существующих ID. Обрыв после успешной записи не порождает новый append при повторе. Ответы проверяются чтением. Строки не удаляются после закрытия закупок; ранее найденные закупки дополнительно сверяются по регистрационным номерам.
- Ошибки входа, оборванная пагинация, потерянная карточка и неполный сбор не считаются пустым успешным результатом. Состояния запуска: `success`, `collected` (без Google), `partial`, `failed`, `interrupted`.
- Каждая выдача ограничена сайтом 10 000 строк; при большой выдаче скрипт делит период по датам публикации. Если даже день превышает лимит, запуск фиксирует ошибку, а не молча отбрасывает строки.
- Задержка между запросами — 1,5 секунды, с ограниченными повторами при временных ошибках. Глобальная advisory-блокировка PostgreSQL предотвращает одновременные сборщики. На сервере общий `flock` разделяет сбор и деплой.

Совпадение означает, что TenderLand вернул кандидата по указанному запросу. Это не заключение о возможности участия и не доказательство, что все слова найдены в названии: совпадение могло быть в документации. Ручная оценка закупки остаётся за сотрудником.

## Локальная разработка

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.lock -r requirements-dev.lock
.venv\Scripts\python.exe -m pip install --no-deps -e .
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\ruff.exe check .
```

Скопировать `.env.example` в `.env`, задать свои параметры. Файл `.secrets/tenderland.json` имеет форму `{"username":"...","password":"..."}`. Ключ сервисного аккаунта — `.secrets/google-service-account.json`. Оба файла и `.env` исключены из Git и Docker build context.

Запуск вне Docker требует `DATABASE_URL=postgresql+psycopg://...`. Миграции не создаются автоматически из моделей:

```bash
alembic upgrade head
tender-search probe
tender-search validate-keywords
tender-search check
tender-search run
tender-search status
```

`probe` проверяет оба режима поиска на одном запросе, ничего не пишет в БД или таблицу. `validate-keywords` проверяет исходные запросы встроенным анализатором синтаксиса сайта. `check` проверяет вход, схему БД и чтение таблицы; запись проверяется командой `sync`/обычным запуском.

Диагностический частичный сбор: `tender-search run --collect-only --limit-jobs 4`. Он сохраняет результаты в БД, но получает статус `partial`, а не полный успех. Повторная доставка уже собранного: `tender-search sync`.

Для интеграционных тестов нужен отдельный PostgreSQL и `TEST_DATABASE_URL`. База тестов не должна быть производственной: тест вставляет и удаляет специальную тестовую запись. CI создаёт собственную БД, применяет миграции, проверяет `alembic check`, дубли, историю и блокировки, затем собирает Docker-образ.

## Сервер

```text
/opt/tender-search/
  bin/             проверенные скрипты запуска и деплоя
  repo.git/        локальный bare-репозиторий
  releases/SHA/    версии исходников
  current -> releases/SHA
  secrets/         TenderLand и Google JSON, вне Git
  shared/.env      параметры сервера и пароль PostgreSQL
  shared/data/     датированные JSON-отчёты
  shared/backups/  дампы PostgreSQL перед миграциями
```

PostgreSQL живёт в отдельном Docker volume `tender-search_pgdata`, порт наружу не публикуется. Контейнер приложения работает под UID 10001; каталог отчётов должен быть доступен ему на запись. Секреты монтируются только для чтения, их каталог и файлы доступны контейнеру через группу 10001. Не выполнять `docker compose down -v` на рабочем сервере.

Первая установка: создать `shared/.env` с уникальным паролем и `TENDER_ROOT=/opt/tender-search`; положить два JSON в `secrets`; установить скрипты из `deploy` в `bin`, а unit-файлы — в `/etc/systemd/system/`. Разовая установка выполняется через временного SSH-пользователя с sudo. Последующая работа root systemd и доступ к публичному GitHub-репозиторию не зависят от срока жизни этого SSH-пользователя.

## Выпуск и автоматическое развёртывание

1. Код пишется и проверяется локально, затем коммитится и отправляется на GitHub.
2. GitHub Actions для `main` запускает линтер, unit/integration-тесты с настоящим PostgreSQL, проверку миграций и сборку Docker.
3. Только после успеха CI передвигает `production` на проверенный коммит.
4. Сервер раз в пять минут проверяет `production`. Новую версию извлекает в отдельный каталог, собирает образ, делает резервную копию БД и применяет Alembic.
5. После проверки схемы атомарно переключает `current`. При неудаче build/миграции текущая ссылка не меняется. Автоматический откат миграции БД не выполняется.

Публичный репозиторий не требует постоянного GitHub-токена на сервере. В GitHub Actions необходим доступ `contents: write` для release job; он явно задан в workflow. Защиту веток при необходимости настраивает владелец репозитория.

Ежедневный таймер настроен на 09:00 `Europe/Moscow`. Он включается после проверки полного цикла записи в Google. `Persistent=true` запускает пропущенную задачу после включения сервера. Деплой-таймер включается отдельно.

```bash
sudo systemctl list-timers 'tender-search*'
sudo journalctl -u tender-search.service -n 100 --no-pager
sudo journalctl -u tender-search-deploy.service -n 100 --no-pager
sudo /opt/tender-search/bin/run.sh status
sudo /opt/tender-search/bin/run.sh sync
```

JSON-отчёт содержит время, статус и полноту запуска. В PostgreSQL остаётся журнал каждого запроса. Во время синхронизации не сортировать и не редактировать автоматически заполняемый лист; для ручных заметок использовать отдельный лист. Исторические категории и запросы сохраняются даже после изменения словаря, поскольку они объясняют первоначальное обнаружение.

## Ограничения первой версии

Web-маршруты TenderLand не являются публичным стабильным API: изменение сайта может потребовать обновления адаптера. Внутренние ошибки сайта и неполные карточки отображаются как неполный запуск. Подробные условия в сканах, недоступные как структурированные поля, не извлекаются автоматически. OCR и анализ документов здесь не выполняются. Поиск по документации использует индекс самого TenderLand.

FastAPI не требуется для фонового задания. Playwright сохранён как инструмент проверки браузерного доступа; рабочий сбор использует обычные HTTP-запросы того же интерфейса, без отдельного платного API. Все версии зависимостей зафиксированы в lock-файлах. Навыки, использованные при реализации: Playwright и Google Sheets; никакие письма сотрудникам не отправляются.
